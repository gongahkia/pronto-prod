# Source review, unanswered questions and timed escalation (Tranche C)

This is the local managed workflow. The PS.Cafe Raffles City data and staff identities are synthetic demo fixtures. Real restaurant approval and real provider delivery have not been established by these tests.

## Business sources

Business staff use the Add information button in the `/client/knowledge` card header to import one public HTTP(S) webpage, upload PDF, Word DOCX, HTML/HTM, TXT, Markdown or CSV, or paste text/HTML. The input modes are mutually exclusive. HTML is converted to readable text without executing or rendering it; DOCX uses the existing Mammoth parser. Operators use the same file extraction service through the tenant Knowledge screen. A title is required. The resulting `knowledge_source_submissions` row and numbered `knowledge_source_submission_revisions` retain extracted text, author, outlet, description, content hash, original/final URL or file metadata, review state and timestamps. Non-PDF document uploads use the existing `text` storage type with original format, filename, parser and checksum in metadata. Original binary files are not archived by this flow. A repeated request key returns the same submission. A failed extraction records `validation_failed` for a titled source; the author can replace the file/URL. Legacy DOC files and scanned-PDF OCR are unsupported.

PDFs must have a PDF signature, supported MIME, at most 8 MB, at most 50 pages, and 30–200,000 extractable characters. Extraction has a ten-second response timeout. Public URLs are resolved on each redirect, pinned to a checked public IPv4 address for the request, restricted to HTTP/HTTPS default ports, bounded to three same-host redirects, eight seconds and 1 MB of HTML. Local, private, link-local, metadata, credential-bearing, cross-host redirect and non-HTML targets fail. There is no crawl. Tests inject a fake DNS/transport and ordinary CI blocks network. Public URL ingestion is a user-initiated operation; operators should review copyright and facts before approval. Extracted text is untrusted evidence, never agent instructions.

Submission never updates active `knowledge_sources` or `knowledge_chunks`. A business member holding `knowledge.approve` reviews the exact pending source revision and records a note. A Pronto operator then stages that reviewed revision into the existing `assistant_drafts` flow. Private testing, separate business assistant-revision approval, and explicit operator publication remain required. Publication rechecks the source revision, reviewer identity, author, operation and checksum in the same transaction that updates RAG. A revised source resets its approval; an earlier staged draft cannot publish it. Updates leave the prior published source active until a new revision passes both gates. Archive requests follow the same gates; publication removes active chunks while retaining the source and an `archived` source-version record. New customer retrieval therefore excludes archived content. Historical approvals remain subject to the separate PRON-73 retention decision; a missing reviewer fails publication closed.

## Unanswered question review

The existing inbound worker creates one `knowledge_review_items` row for an escalation caused by low retrieval confidence, missing/invalid citations, weak grounding, a model handoff, or an explicitly flagged source conflict. The row links the tenant conversation and message. A flagged conflict includes source links and conflicting claims from reviewed source metadata. The PS.Cafe reservation-cutoff example has a declared 5:30pm versus 6:00pm conflict; reservation-timing questions escalate rather than quote either value. Other booking availability requests continue through the existing read-only connector.

Business staff can open the secure conversation and submit a correction from the review item. That creates a normal pending `knowledge_suggestion`, which follows the Tranche B exact-revision approval and operator publication gate. Only publication marks the review item resolved. It does not send a reply, change the escalation status, or release AI ownership. A responder must still handle the original customer conversation.

## Timed staff notifications

The existing `staff_notification_jobs` table now contains `initial`, `reminder` and `backup` jobs. Initial notification remains immediate. A configured policy target and verified initial staff destination allow `reminderMinutes` elapsed-time offsets from escalation creation. A verified backup destination gets one job at the configured response target. No target or no matching verified destination means no corresponding timed job. An empty staffed-hours map means continuous coverage for legacy policies; a nonempty map defers a due action outside defined hours to the next staffed minute. UTC-minute scanning handles DST gaps and repeated hours according to actual local wall time. Targets are operating preferences, not response guarantees.

Jobs persist through worker restarts and use the existing claim, lease, retry and uncertain-send handling. Scheduling is idempotent per escalation, kind, policy version and offset. Changing policy cancels pending old jobs and schedules new ones. Before sending, the worker rechecks policy version, conversation ownership, escalation state, and whether a staff resolution reply was queued. Resolved or AI-released handoffs cancel timed jobs. Timed sends require an explicitly verified staff destination; they never infer a backup from a customer channel. A definite failure retries with bounded backoff; a timeout or expired sending lease becomes uncertain and needs operator reconciliation. Accepted sends retain the provider or local SMTP message ID and transport kind. `sent` means the transport accepted the notification; it is not proof a person received it. Exactly-once external delivery is not claimed.

If an escalation arrives outside configured staffed hours and the policy contains an out-of-hours acknowledgement, the existing customer holding reply uses that approved text. The acknowledgement is still queued through the normal outbox and does not change ownership.

The operator Operations screen shows staff job status, scheduled/retrying counts and failures. Knowledge & Connections shows source/review queues. The business Needs Attention and Business Knowledge screens show actionable review work without raw job payloads. The existing Settings form edits the versioned policy. Real staff messaging channels remain disabled pending provider authorization; the local Mailpit test captures actual SMTP reminder and backup messages.

## Local verification

Verify `DATABASE_URL` and `PRONTO_TEST_DATABASE_URL` point to the same marked disposable loopback `pronto_test` database, then run `pnpm test:db:verify` and `pnpm migrate:test` to apply migrations 038–044. `pnpm test:db` covers source review, RAG exclusion/publication, archive invalidation, knowledge review and scheduling. `pnpm test:local-mail` requires loopback Mailpit and captures real local reminder/backup SMTP. `pnpm test:e2e` covers the existing portal routes. The source URL tests use controlled injected responses; neither normal CI nor these commands fetch public websites. Production migration, real provider channels, source retention periods and customer-facing publication require separate review.

The migrations are additive. Before any later production rollout, take and verify a database backup and rehearse migration on a staging copy. A rollback after source publication should use a reviewed compensating migration and restore plan; dropping these tables would discard approval and delivery evidence. PRON-73 still governs long-term audit retention.
